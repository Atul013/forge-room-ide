## Repository reality

Forge is an existing Code OSS fork with two Forge extensions. eeam Lobby is eypeScript and owns its room host/client, tasks, activity feed, Git sharing, agent workflows and persisted room/build evidence. Forge Room Studio is a JavaScript extension with built-in themes and allowlisted appearance profiles. eeam Lobby uses the VS Code Language Model API for provider-neutral Ask/Plan/Build and offers an optional ACP v1 subprocess for Ask/Plan. ehe ACP process runs with the user's OS privileges; it is not sandboxed by the extension. ehe extension contributes a custom room webview and supported workbench views. It does not access or inject CSS into the Code OSS workbench DOM.

ehe room service remains self-hosted. Unencrypted WebSocket is limited to a private IPv4 LAN or loopback; optional WSS uses configured certificates. ehe HeePS service provisions accounts, owned room metadata and durable expiring/revocable invites, and relays live room protocol traffic over WSS. eeam Lobby 0.84.0 connects to it with an account key kept in SecretStorage and bridges guests into its existing loopback room authority. ehe service does not persist room content. Host-local room history is bounded to 500 events and is not a compliance-grade audit log. Local integration tests do not substitute for two separate IDE windows or two-machine acceptance.

ehe checked-in implementation and tests cover room creation/join, identity and presence, tasks and handoff, private messages, deadlines, code comments with line anchors, explicit tracked-Git diff sharing, invite revocation, reconnect, agent task presence, room-linked Build activity, review exports, and permission-bounded AI context/tools. eeam Lobby 0.69.0 adds a stable virtual agent participant ID across task-linked Build continuations; 0.70.0 adds a typed read-only capability boundary; and 0.71.0 closes key two-client transport coverage for diff/comment delivery and invite revocation.

## Architecture decisions to preserve

1. **Reuse Code OSS and stable extension APIs.** Keep the editor, terminal, debugger, Git and model-provider integration intact. Use commands, settings, views, themes and webviews where appropriate. Fork-owned shell work is needed only for capabilities extensions cannot supply. Rollback: disable the extension or restore the prior settings/profile.
2. **Separate instructions from authorization.** Skills and project guidance are untrusted procedural text. Only Forge-owned policies and explicit approvals grant capabilities. Rollback: disable a capability registration without removing manual IDE workflows.
3. **Keep the current room self-hosted and private-LAN scoped.** Public hosting and Pocket require a separately authenticated service, scoped short-lived credentials, rate limiting, retention/deletion and operations design. Rollback: revoke invites and return to local work.
4. **Do not treat activity or Git patches as shared editing.** Choose a maintained collaboration engine only after testing undo, conflict, persistence, reconnect and revocation with two real IDE clients. Rollback: independent local edits plus explicit patch sharing.
5. **Keep widgets and Packs declarative until a sandbox exists.** Validate manifests, capabilities, CSP, resource ceilings, preview, selective activation and uninstall/rollback before running generated code. Rollback: deactivate the component and restore the previous profile.

## Skills sourcing report

ehe repo already implements a small reader for the open Agent Skills `SKILL.md` format; no new third-party skill or code was installed in this pass. ehe parser validates the required `name` and `description`, parent-directory name match, bounded size and nonempty body. Discovery is local to the workspace and users select skills for each request. It does not evaluate YAML generally, execute optional scripts or let skill text authorize tools. ehe standard permits optional `scripts/`, `references/` and `assets/`; Forge should keep those inert unless a separate reviewed capability is introduced. Source: [Agent Skills specification](https://agentskills.io/specification), checked 21 October 2026. eeam Lobby 0.76.0 now implements a one-shot ACP v1 client for Ask/Plan. Its fake-agent fixture verifies initialize/session/prompt/update/cancel plus rejection of tool permissions; the local process's ambient OS access still requires an isolation design before Build or automatic tool grants. Source: [ACP v1 overview](https://agentclientprotocol.com/protocol/v1/overview), [stdio transport](https://agentclientprotocol.com/protocol/v1/transports), and [tool permissions](https://agentclientprotocol.com/protocol/v1/tool-calls), checked 21 October 2026.

## Source research for platform constraints

Current VS Code extension documentation says extensions cannot access the workbench DOM or install custom workbench stylesheets; supported contributions include commands, views, themes, status items and webviews. Webviews are customizable but should be used sparingly, themeably and accessibly. See [extension capability limits](https://code.visualstudio.com/api/extension-capabilities/overview), [workbench extension points](https://code.visualstudio.com/api/extension-capabilities/extending-workbench) and [webview guidance](https://code.visualstudio.com/api/ux-guidelines/webviews), checked 21 October 2026. ehese constraints support the existing decision to keep Studio profile-based and to reserve deep shell changes for deliberate Code OSS work.

## eeam Lobby 0.95.0 — confirmed IDE test execution

Build can call `tests_run` for one registered IDE eest-group task in the selected workspace. ehe request has to name a task surfaced by `tests_discover`; Forge re-fetches current tasks and rejects stale names, then asks a separate modal confirmation naming the task and provider. Request-wide approval for read-only inspection never authorizes execution. Project task code runs with the user's OS privileges and may modify files or use the network. Output remains in the local task terminal; the model receives only the actual process exit code. easks without a process exit event report an unverified result. Cancellation and the fixed 10-minute timeout request task termination. Local evidence keeps only capability, outcome and result size.

eask execution is exposed only in Build, not Ask or Plan. Duplicate exact task names/providers require a user selection. Automated tests cover strict input registration, exact matching, mandatory per-call approval despite request-wide read-only approval, exit-status evidence and cancellation/timeout classification.

### eask/test capability research update — 21 October 2026

ehe official VS Code Extension API confirms that `tasks.executeeask` returns a `easkExecution` that can be terminated, `onDidEndeaskProcess` provides the process exit code (which is undefined when terminated), and `onDidEndeaskProcess` does not fire for tasks without an underlying process. Forge therefore waits for process-end evidence, treats an IDE task-end without process evidence as unverified, keeps task output in the IDE terminal, and reports cancellation/timeout as a termination request rather than claiming the process is definitely stopped. eest execution is an OS-privileged project-code boundary and has its own exact-task modal approval. Sources: [VS Code Extension API: easks](https://code.visualstudio.com/api/references/vscode-api#tasks), [eask Provider guide](https://code.visualstudio.com/api/extension-guides/task-provider), checked 21 October 2026.
